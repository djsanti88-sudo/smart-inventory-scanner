| DC-1 | Money bug (unmetered spend) | `src/server/decode/pipeline.ts:1412-1435` (runGoUpc / chargeOnEgress), `src/server/upc/GoUpcProvider.ts:243` (`deps.gate.run`), `src/services/upc/goUpcThrottle.ts:35-60` (GoUpcGate, no cancellation API), `src/server/decode/pipeline.ts:82` (module-level singleton `goUpcGate`) | The Go-UPC rung's real network call is gated behind a **module-level, process-wide** `GoUpcGate` that serializes ALL concurrent requests at `minGapMs=500ms` (2 req/s) with **no cancellation mechanism** - `run()` just queues a promise on an internal `tail` chain that always eventually fires. `chargeOnEgress()` (the daily-cap charge) is called *inside* the `client` callback passed to `gate.run`, i.e. only once the throttle releases that request's turn - not when the rung starts. Meanwhile `runLadder` (`src/server/upc/ladder.ts:94-140`) races each rung against a per-rung budget timer (`DECODE_LADDER_RUNG_MS`, default 8000ms for goupc - the wave-3 realistic budgets only apply to fetchv2/gpt). `runGoUpc` never reads `ctx.signal` and `goUpcLookup` is never passed the ladder's AbortSignal, so an abandoned rung keeps running to completion regardless of the ladder giving up. Under the documented real usage pattern of a bulk scan burst (aiSpendGuard.ts's own comment references "a fast 300-code run"), any request whose turn in the shared queue is more than ~8s away (the 17th+ concurrently-queued Go-UPC lookup, at 500ms spacing) will have its ladder-level `Promise.race` lose to the timeout BEFORE `client()` (and therefore `chargeOnEgress()`) is ever invoked. `withPaidChargeArmed`'s `finally` then disarms `paidChargeArmed=false` for that request. Seconds later, when the gate finally releases the orphaned call, `client()` runs: `chargeOnEgress()` is now a no-op (arm already cleared, no throw) but the code unconditionally proceeds to `return goUpcLookup(c, d)` - a **real, billed Go-UPC API call** that spends money and increments Go-UPC's own monthly usage counter (`deps.usage.record()` in GoUpcProvider.ts, called only after the real fetch resolves), while the app's own daily AI-lookup cap (`AI_LOOKUP_DAILY_LIMIT`, the primary bill-drain guard per aiSpendGuard.ts's own module doc) is **never charged** for it, and the result is discarded (nothing awaits the orphaned ladder rung anymore). This directly violates "the daily cap charges ONLY paid rungs, exactly once per genuine compute" - here a genuine paid compute is charged **zero** times, the inverse of the L12 double-charge defect but the same class of harm (the cap can no longer bound real spend during a burst). | High | Medium-High (mechanism is unambiguous in the code; triggering requires either high concurrency or an existing queue backlog on the shared `goUpcGate`, which a genuine bulk-scan session or a slow/degraded Go-UPC endpoint would produce) | Thread the ladder's `AbortSignal` (`ctx.signal`) into `runGoUpc` and `goUpcLookup`'s fetch (same pattern already used for the GPT rung, see `runGpt`/`maybeGptLadder` threading `opts.signal` into `gptFromScratch`), and/or give `GoUpcGate` a way to reject/skip a queued entry once its owning request's deadline has passed instead of always eventually firing it. As a cheaper mitigating fix, move `chargeOnEgress()` to fire when the rung *enters* the gate queue (spend-intent) rather than when it is dequeued, or make the charge itself abort-aware so a request that the ladder already gave up on never lets its queued Go-UPC call execute unmetered. ## Notes on invariants checked and found sound
- **Cheapest-first, pay-once (single-rung case):** `buildFreeLadderRungs`/`buildPaidLadderRungs` in `src/server/upc/ladder.ts:170-210` order rungs correctly (upcitemdb -> openfoodfacts -> goupc -> fetchv2 -> gpt), and `runLadder` stops at the first `settled:true` outcome. Sound for the non-escalation path.
- **Atomic conditional daily-cap increment:** `chargeDailySlotConditional`/`incrementIfBelow` (`src/services/security/aiSpendGuard.ts:221-231`, `src/server/upc/storage.ts:495-532`) use a single atomic SQL upsert with a `WHERE value < limit` guard and `RETURNING`, so the check-then-charge race the item-1 fix targeted is genuinely closed for both Turso and the single-process file adapter. This part of the branch's own recent hardening looks correct.
- **Gemini out of decode:** `GEMINI_DECODE_DISABLED = true` (`pipeline.ts:77`) is a hardcoded literal, not an env var, and gates both the Plan D grounding arm and (transitively) the escalation providers. Confirmed no live decode path can reach Gemini.
- **God account cost-truth:** every god-account bypass (`assertPaidCapAvailable`, `settlePaidCharge`, GPT `$`-budget, Go-UPC monthly cap) still calls the underlying charge/record function unconditionally for god; only the throw/block is skipped, matching the 2026-08-09 owner ruling.
- **`decodeOrchestrator.ts`:** confirmed types-only/deprecated; nothing in the reviewed section imports functions from it beyond type re-exports already flagged as expected in project docs.
