## Sound (checked under the failure/recovery lens, no defect found)

- **Firestore transactional apply + idempotency-key retry** (`src/services/db/firebase/firebaseSyncTarget.ts:102-259`): a client-side timeout (`withTimeout`, 55s) that fires while the underlying `runTransaction` is still committing server-side does NOT create a double-count risk. If the transaction actually commits after the client gives up and the item is requeued, the retry's fresh `runTransaction` call reads the `_appliedKeys/{idempotencyKey}` marker first (all-reads-before-writes, Firestore transaction rule honored at `:141-153`) and returns `alreadyApplied: true` without re-writing the count. This was verified by code read only, not by re-running `npm run test:firebase` in this loop (the suite that actually exercises the emulator-backed `.rules.test.ts` files) — labeling this **inspected-sound, not freshly proven** per the task's testing-honesty requirement.
- **Ledger replay order-independence** (`src/services/inventory.replay.ts:8-27`): `replayLedgerCounts` processes events in whatever order the caller passes them, without an internal sort. This looked like a clock-skew risk at first (createdAt is client-set physical time per project law, so two devices with skewed clocks could produce a stream that is not truly chronological) but `applyScanEventOnce`'s dedup-by-`scanEventIds`-membership makes the final quantity a sum over a SET of applied event ids, which is order-independent — a reordered replay converges to the same total regardless of clock skew between devices. No defect found here.
