## What was checked and found SOUND

- **Scanner focus discipline (`ScannerInput.tsx`)**: input auto-focuses on mount (line 75), Enter always calls `submit()` and never a nearby button (dedicated `onKeyDown` on the input only, `handleKeyDown` line 134), the buffer is the input's own uncontrolled DOM value (not per-keystroke React state) so rapid injected keystrokes are never dropped, and `submit()` always clears + refocuses the input (line 130-131) after every scan including error/unknown outcomes. Backed by a running test suite: `src/components/scanFocus.test.tsx` (auto-focus on load, refocus after known scan, refocus after unknown scan, no `clear-cache` control present on the Scan page) executes under `npm run test` (`dom` project) — this is a real, executing guard, not a dead test.
- **Dangerous actions kept away from the scan flow**: `src/app/(app)/scan/page.tsx` deliberately collapses "Start session / Finish session / Clear session" (line 225-233, has a `window.confirm` guard) and Export/Sync controls inside a closed `<details>` (line 179, `open={expandSecondary}`) for real users — collapsed `<details>` content is not in the tab order in any browser, so a stray Enter from the scanner cannot reach these buttons. Clear Cache is explicitly kept off the Scan page entirely per a code comment (line 234-235) and is proven absent by `scanFocus.test.tsx`. `LiveScanFeed`'s inline approve/decline suggestion buttons are hardened against scanner-Enter theft: `tabIndex={-1}` + `onMouseDown={(me) => me.preventDefault()}` (lines 187-208, 279-281) so they can never receive focus via Tab/scanner input and mouse-down never steals focus.
- **TOP-LEVEL LAW visibility**: every scanned code — known, unknown, conflict — is pushed into `scanFeed` synchronously before any network/decode work (`scanStore.ts` line 3547 push, then `ensureProvisionalCount` line 3553 counts it before any await), and `LiveScanFeed` renders every row via `scanFeed.slice(0, renderWindow)` with a "+N earlier scans counted / Show more" affordance (lines 72-73, 273-289) rather than ever dropping rows — the visible-window truncation is display-only; the header count (line 79, `{scanFeed.length} scans`) and all totals are computed off the full array, not the window.
- **No private-field leakage found**: grepped `src/components/**` for `cost`/`margin`/`costPrice`/`wholesalePrice` — the only hits were unrelated CSS/comment matches ("margin alone (4px)"). `FinalCountTable.tsx` and `LiveScanFeed.tsx` both gate raw code / match-type / lookup-key columns behind `useIsPlatformOwner()` and route customer-facing names through `customerDisplayName()`/`prettifyProductName()`.
- **`FinalCountTable.tsx` totals are correct and independent of UI-1**: it reads `finalCounts` (the authoritative ledger) directly via `sessionCounts`/`rows` (lines 65-100), never `scanFeed`, so it is not affected by the `resolveUnknown` status rewrite that causes UI-1.

## What could not be verified statically (needs browser proof)

- Whether a real hardware scanner's rapid keystroke-then-Enter burst (sub-20ms injection) ever races the `debounceMs` fallback timer in `submitMode: "both"` such that a double-submit or partial-buffer submit occurs — the code structure (uncontrolled ref value, `clearTimeout` in `submit()`) looks correct, but this needs a live/rapid-scan Playwright or physical-scanner test, not static reading.
- Whether the collapsed `<details>` truly stays closed on first paint for a real (non-E2E) production build across browsers (Safari has historically had `<details>` quirks) — `expandSecondary` is computed from `process.env.NEXT_PUBLIC_E2E_AUTH_BYPASS`, which is correct at the source level, but actual first-paint rendering needs a browser check.
- The UI-1 scenario itself was traced through code, not exercised in a running app — recommend a Playwright/RTL regression test that scans an unknown code, resolves it via Needs Review, and asserts the Scan page's "Qty on hand" cell for that row is a real number, not "-".

## Scenarios most wanted in an E2E/browser suite

1. Scan an unrecognized barcode → resolve it in Needs Review (link to existing product) → return to the Scan page and assert the resolved row's "Qty on hand" cell shows the real count, not "-" (proves/regresses UI-1).
2. Fire a burst of 20+ scans with <20ms gaps between keystrokes and Enters (simulating a real hardware scanner) and assert scan count === feed row count === session total, with the input always ending focused and empty.
3. With the Scan page's secondary `<details>` collapsed (default, non-E2E build), Tab from the scan input and confirm focus never lands on "Clear session" or any button inside the collapsed section.
