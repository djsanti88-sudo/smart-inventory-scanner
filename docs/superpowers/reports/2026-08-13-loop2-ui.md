## Job 2 — New lens: the unhappy path on screen

**UI2-1 (new, Medium-High severity, High confidence) — the only aggregate sync/offline indicator on the Scan page is hidden inside a collapsed `<details>` by default for real users.**
`src/app/(app)/scan/page.tsx:179` wraps "Sessions and export" — including `<SyncStatusBar />` (line 261) — in `<details open={expandSecondary}>` where `expandSecondary = process.env.NEXT_PUBLIC_E2E_AUTH_BYPASS === "1"` (line 89), which is **false** in production and only true under the Playwright E2E webServer. `SyncStatusBar` is the only surface showing online/offline, pending-sync count, "Saved locally, not synced yet", "Some items haven't saved yet. Tap Try saving again", and the Retry button (`src/components/SyncStatusBar.tsx`). `Nav.tsx` has no sync indicator (grepped, no hits). The per-row `SyncBadge` in `LiveScanFeed` (last column, `feed-qty` and product columns come first) is the only other signal, and on a narrow/phone viewport it sits past the horizontally-scrolling region loop1 already flagged (`role="region" aria-label="...scroll horizontally for more columns"`). Net effect: a shop worker scanning on a flaky connection sees large, confident, correctly-rendered quantities everywhere in the primary viewport (ScannerInput's 4xl "on hand" number, LiveScanFeed Qty, FinalCountTable Qty) with **no visible cue anywhere above the fold** that some of those counts have not yet reached the server, unless they think to click "Sessions and export" to expand it or scroll the feed table sideways to see a "Not saved yet" badge. This is exactly the "confident value shown while the underlying state is pending/failed" pattern the task asked to hunt for — not a false number, but a real omission that could let a shop close out a session believing everything saved when `pendingSyncQueue` is non-empty. Existing e2e coverage (`offline-retry-idempotency.spec.ts`, `persist-corruption-recovery.spec.ts`) runs under `IS_E2E=1` / the auth-bypass flag, so the `<details>` is always pre-expanded there — **this collapse-hiding behavior for real (non-E2E) users is not exercised by any existing test.** Needs browser proof to confirm the exact collapsed rendering on first paint, but the code path is unambiguous.

**Checked and found sound (no new issue):**
- `ScannerInput.tsx`'s big confirmation-panel quantity (`PANEL_STYLES`, all statuses including `resolved`) reads `liveFeedEntry ?? lastResult`, i.e. it subscribes live to the same `scanFeed` row the fix updates — so the UI-1 fix's correctness also flows through to this panel automatically; no separate stale-number risk there.
- `SyncBadge`/`FinalCountTable`'s per-row Sync column are honestly labeled ("Saved", "Not saved yet", "Save error") and are a separate column from the quantity, not commingled into a false "verified" claim.
- `NeedsReviewTable`'s "Look up with AI" / "Deep lookup" buttons are correctly `disabled={!aiEnabled}` with an honest title tooltip — no "AI lookup: On" style lie found there.
- The `ignore` review action returns early in `resolveUnknown` (scanStore.ts:6238-6249) before touching `scanFeed`/`productId`, so it cannot interact with the UI-1 merge-quantity logic at all.
- No live path currently sets `status: "ignored"`/`"unknown"` on a `ScanEvent` (confirmed by grep, matches loop1's UI-2 note) — the Qty column's `"-"` fallback for those statuses is currently dead code, not a live gap.
- Long product names / part numbers: `LiveScanFeed`'s Product cell uses `truncate` only on the suggestion text, and the Qty cell is a separate `shrink-0`-adjacent-free plain `<td>` in a horizontally-scrolling table — a long name cannot visually push or clip the quantity number off-screen; the whole row just scrolls.
