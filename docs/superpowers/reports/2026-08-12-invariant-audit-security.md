## Most dangerous finding (leads the summary)

**Claim 1 (server-only API keys) is the weakest enforcement found.** `src/services/keySafety.test.ts`
only scans five hardcoded client directories for a literal substring match — it does not walk the
import graph. A new helper module placed anywhere else (most plausibly under `src/services/**`,
which the test never touches) that reads `process.env.OPENAI_API_KEY` or similar and lacks the
`import "server-only"` guard would pass this test today even if a client component imports it and
Next's bundler inlines it into the browser bundle. This is exactly the audited defect shape: the test
*looks* like a guard and is named like one ("API key safety"), but its coverage is a fixed directory
allowlist plus literal-string grep, not the transitive "is this reachable from the client bundle"
property CLAUDE.md and GUARDRAILS.md actually claim ("client code must never read
`process.env.*_API_KEY`" — no qualifier limiting that to five specific directories).

**Second finding worth flagging:** the daily-cap single-charge invariant (claim 2) is real today but
rests on two independently-written boolean checks (`route.ts:628` and `route.ts:821`) both deriving
from the same client-supplied `body.mode` string rather than one shared guard function — a duplicate-
condition pattern that is exactly how the original L12 double-charge bug (232 charged vs ~27 genuine
calls) was described as having happened.

Everything else in scope (Gemini kill flag, evidence-truth self-claim rejection, Firestore path-based
tenancy) is either genuinely code-enforced or a documented/self-skipping test rather than a hidden gap.
Claim 5 (sanitizer-before-provider-call) could not be fully confirmed or refuted in the time available
and is flagged for follow-up rather than asserted either way.
