# Technical Decisions

Why each choice was made. Newest decisions at the bottom of each section.

## Stack
- **Next.js 16 (App Router) + React 19 + TypeScript** — generated by `create-next-app`. The
  folder was empty, so a fresh app was the correct starting state. Next 16 ships breaking changes
  vs older training data; the bundled docs in `node_modules/next/dist/docs/` were consulted before
  writing app code (route handlers use Web `Request`/`Response`; pages/layouts are server
  components by default; `params` is a Promise).
- **Tailwind v4** — create-next-app default. CSS-first (`@import "tailwindcss"` in globals.css),
  single `postcss.config.mjs`, no JS config. Lower friction than v3 for this setup.
- **npm** — no pnpm on the machine; `--use-npm` forces it.
- **No Turbopack** (`--no-turbopack`) — lower-risk default alongside Vitest/Playwright. Can opt in later.

## State
- **Zustand v5 + persist (localStorage)** for local optimistic scan state. Chosen over Context
  (perf, testability) and Redux (not already in repo, heavier). Spec explicitly prefers Zustand.
- **`skipHydration: true` + `_hasHydrated` guard + `<StoreHydrator>`** — avoids the App Router
  hydration mismatch where the server renders empty state and the client rehydrates from
  localStorage. We rehydrate in a mount effect and gate persisted-state UI until hydrated.
- Store module is `"use client"` and never imported by a server component (would pull
  `localStorage` into the server bundle).
- **IndexedDB** is the documented next upgrade if localStorage limits are hit.

## IDs and idempotency
- **`crypto.randomUUID()`** for ScanEvent ids and keys — native in Node 24 and the browser on
  localhost (secure context). No `uuid` dependency.
- Services take an **injectable `idFactory`/`now` clock** so unit tests are deterministic
  (no reliance on real time/randomness inside pure logic).
- **Idempotency key generated ONCE at scan time** and reused on every retry. Key format:
  `${businessId}:${sessionId}:${scanEventId}:${operation}`. Never regenerated inside retry — that
  would defeat dedupe and double-count. The mock DB dedupes upserts by id / key.
- **InventoryCount.scanEventIds** is the dedupe ledger: an event id already present is never
  applied again (`applyScanEventOnce`).

## Testing
- **Vitest projects split**: `unit` (node env, `src/services/**/*.test.ts`, no React/next) runs
  fast and isolated; `dom` (jsdom, components + store) uses the React plugin. `@/` alias mirrors
  tsconfig via `fileURLToPath`.
- Pure services contain NO React or `next/*` imports so the node project never needs jsdom — this
  is also why matching/cleaning/idempotency/CSV/circuit-breaker are plain TS functions.
- **Playwright** for E2E proof, `webServer` auto-starts `next dev` on **pinned port 3100**
  (`reuseExistingServer: !CI`) to avoid Windows port flake. Proof screenshots written explicitly
  to `e2e/proof/`. One-time `npx playwright install chromium` required before first E2E run.

## AI
- **Mock provider by default.** Real Gemini (primary) / OpenAI (fallback) are STUBS that only
  activate with env keys + explicit opt-in, and run **server-side only** in `/api/ai-lookup`.
- AI runs only for **unknown** codes, after the deterministic sanitizer, behind a **daily-cap
  circuit breaker**. Never for known matches. Never while offline. Never decides inventory math.

## Code cleaning / matching
- `cleanCode` preserves case and internal spacing of messy labels; `normalizedCandidates` adds
  before-`%`, hyphen-stripped, and whitespace-stripped variants (ordered specific -> general).
- Matcher labels `matchType` accurately (exact_alias / normalized_alias / primary_barcode /
  primary_sku / gtin / upc / ean / unknown / conflict). A code mapping to >1 product = `conflict`
  -> Needs Review, never guessed. All matching scoped by `businessId`.

## Evidence verification + cross-check (live AI decode)
- **Principle:** AI may claim exactCodeEvidence; the app verifies independently. The model's
  self-claim is never trusted - only `EvidenceVerifier` decides.
- **EvidenceVerifier** returns `{verified, strength, matchedCode, matchedSources, reason}`. Strength
  tiers none<url_only<snippet<grounding_chunk<fetched_source. Numeric codes compared with spaces/
  hyphens removed; vendor codes need exact token match (word boundaries). url_only verified only
  from a trusted host allowlist.
- **CrossCheckEngine** uses brand similarity + name token Jaccard + barcode comparison +
  contradiction detection (no productName string equality) -> agree/conflict/single_provider/weak.
- **decideDecode** gate: "verified" requires public barcode + strong app-verified evidence +
  agreement (or single) + identity + confidence>=threshold. Vendor/FNSKU/internal never verified.
- **Route** gained a "decode" mode (dual provider + server-side verify + cross-check). `IS_E2E=1`
  forces mock-only so E2E can never spend tokens; `page.route` mocks the endpoint in E2E; unit tests
  mock the engines and `fetch`. No live tokens in `npm run test` or `npm run test:e2e`.
- **Why keep human approval even for "verified"?** The previous bug came from trusting AI; verified
  decode is a strong signal but the owner stays in control. Auto-accept is opt-in.

## Resolver accuracy hotfix (product identity)
- **Bug:** an AI auto-accept feature trusted AI guesses as verified identity and persisted them as
  deterministic aliases (855724007602->Laird, 078742051451->Leviton, X004DY7YUT->Amazon FBA Label).
  See RESOLVER_AUDIT.md. Root cause: no trust boundary between AI suggestions and verified data.
- **Fix - explicit trust flags:** `Product.verified` and `Alias.approved`. The deterministic
  resolver returns `known` only from approved aliases / verified products. Seed = verified/approved;
  human resolution sets them true; AI never writes these tables.
- **Fix - AI is suggestion-only:** removed auto-accept and auto-fire. `lookupUnknown` only populates
  `suggested*` + `verifiedFacts`/`guesses`/`reason` on the review and stays `open`. A human approves.
- **Fix - vendor labels:** `detectCodeType` now classifies X0/B0 10-char codes as `vendor_label`
  (checked before SKU/digit rules) and they route to Needs Review unless a human-approved alias exists.
- **Fix - new ProductResolver** (`src/services/resolver.ts`) returns ResolverResult with
  `resolverStatus` (known/needs_review/conflict), `codeType`, `reason`, confidence. Purely
  deterministic; never emits AI/"suggested"/"mock" identity.
- **Fix - purge poisoned cache:** persist `version` 2->3 migrate resets products/aliases to seed and
  clears session/queues (keeps settings). Plus a `clearLocalCache` action + "Clear local cache" UI
  button (Scan + Settings) that also wipes the mock DB localStorage.
- **Why not add a barcode-lookup API?** Out of scope for the hotfix and would reintroduce external
  trust. Deterministic-first + human approval is the correct fix; a verified catalog import or
  approved barcode provider can come later behind the same approval gate.

## Auth / data
- **Local mock auth** (localStorage flag + demo login). Firebase Auth/Firestore is a documented
  future path only; `.env.example` lists the names.
- **Semantic firewall**: scanned codes, CSVs, AI results, notes are untrusted data — never obeyed
  as instructions. Sanitizer masks PII + cost/price/margin before any AI call.

## A/B/C batch (2026-06-14)
- **Configurable decode budget — clamp server-side, do NOT bump persist version.** `Settings.decodeBudgetMs`
  is owner-set in the UI and sent to the route, but it is client-supplied (untrusted), so the route clamps
  it to [5000, 20000] (`decodeBudget.ts`). The plan said "bump persist version 3 -> 4"; that was rejected
  during implementation because the existing `migrate` resets products/aliases/finalCounts to seed — bumping
  would WIPE the user's learned data just to add a settings field. Instead the field is read defensively
  (`?? 13000`), so old persisted settings work without a migration. (Smallest safe change; data safety.)
- **Junk cleanup is reversible by snapshot, restored additively.** `cleanupJunkCounts()` snapshots the exact
  removed counts/products/aliases into a persisted `lastCleanupBackup`; `undoCleanup()` merges them back by
  id (not a full-state overwrite) so any scans made after the cleanup are preserved. A product/alias is only
  removed when no surviving good count references it, so good rows can never lose their product.
- **Backup before touching data.** The Settings button downloads a full JSON snapshot
  (`inventory-backup-before-cleanup.json`) before removal. `inventory` is not a git repo, so the JSON backup
  + in-app Undo are the only rollback paths — hence both, not one.
- **Junk-present cleanup E2E uses a v3 localStorage seed.** The firewall now prevents creating junk, and the
  persist `migrate` clears `finalCounts`, so junk can't be produced via the normal flow in a test. Injecting
  a persisted blob whose `version` equals the store version (3) skips `migrate` and lets seeded junk survive
  to be cleaned. Store-level tests remain the authoritative proof of the cleanup/undo logic.

## Shared catalog + recommendation-first cleanup (2026-06-14)
- **Provider abstraction, no cloud dep (owner Q1=A).** `CatalogProvider` is the seam; `localCatalogProvider` (pure,
  offline-first) is the only impl now. A future Supabase/Postgres/Firebase impl satisfies the same interface with no
  caller changes. Catalog data lives in the persisted store (3 new slices), not a cloud DB.
- **Lookup order correction (owner).** Private shop override is checked BEFORE the global catalog, so an override
  beats global data. Order: local resolver -> shop override -> verified catalog -> weak/AI -> Needs Review.
- **Verified STATUS, not a confidence floor, gates auto-resolve.** First cut required `confidence >= 0.5`; that wrongly
  rejected owner-verified entries with no numeric score. An entry is trusted because its status is `verified` (set only
  by owner/admin/trusted source), regardless of confidence. (Bug caught by re-running tests in the correct directory.)
- **AI can never overwrite a verified catalog entry (owner rules #1/#2).** `applyAiCandidate` only observes/appends
  evidence on a verified entry; it never changes identity or status. AI writes are `pending`; only owner approval writes
  `verified`. Enforced + unit-tested.
- **Privacy by type separation (owner rules #3/#4/#6).** `CatalogEntry` (global) has no businessId/price/notes; private
  data lives in `ShopOverride`/`feedbackEvents` (businessId-scoped). `sanitizeCatalogEntry` drops unknown fields, masks
  PII/cost via the existing sanitizer, and restricts URLs to http(s). Junk names are rejected by the firewall.
- **Cleanup is recommendation-first; the owner presses the final button (owner Q5=C).** A pure engine produces
  grouped, explained, confidence-scored recommendations; `applyCleanupSelections(ids)` removes only the selected rows
  with a JSON backup + additive Undo. High-confidence defaults checked, weak/conflict unchecked. Verified/seed/manual
  and still-counted products are never offered for removal.
- **Process note (doctrine clean-env gate):** a bare `vitest run` ran in the parent directory and matched 528 unrelated
  test files (false green). Always run inventory commands with an explicit `cd`. Re-running correctly surfaced 3 real
  failures that the false green had hidden.

## Confidence-based auto-verify (2026-06-14, speed-first)
- **Score the existing decode response - zero extra network calls.** The owner's real decode is fast (~3-4s) and
  accurate; the auto-verify gate runs synchronously on `decision` + `best result` + cited source URLs that the route
  already returns. No new fetch/search step was added (a budget-gated escalation remains a documented future option).
- **Evidence drives the score, not the AI's confidence number.** Deterministic 0-100 with caps (AI-only <=60,
  Tier-3-only <=79, Tier-4 <=50). Verified STATUS / exact-barcode evidence (from EvidenceVerifier) is the trust signal.
- **Safety gates run BEFORE the threshold.** Conflict-with-verified, junk source, no-exact-evidence, AI-only, vendor
  code, private data -> Needs Review regardless of score; lowering the threshold cannot bypass them.
- **Policy change (reconciled):** the blanket `autoAddDecodedProducts` auto-add (verified OR suggested) is replaced by
  confidence-gated auto-verify. Suggested-without-exact-barcode-evidence now goes to Needs Review instead of being
  auto-counted. `autoAddDecodedProducts=false` is kept as a master "manual mode" gate. Updated the 4 tests that
  encoded the old behavior (not weakened - re-pointed to the new intent).
- **AI never overwrites verified - enforced at two layers:** catalog-first short-circuits AI when a verified entry
  exists (so AI never even runs), and `planAutoVerify` flags a verified-catalog conflict to Needs Review as a backstop.
- **Trusted-source toggle has teeth:** when off, a trusted (Tier 1/2) source is treated as merely "supporting" for
  BOTH points and caps, so it can't shortcut auto-verify on its own. (TDD caught that the first cut only reduced points.)
- **No persist-version bump; settings read defensively** (`?? default`) so existing catalogs/aliases/counts are intact.

## Hotfix: verified-decode fast path (2026-06-14)
- **Bug:** the Tier-3 single-provider cap (`min 79`) capped the MOST COMMON success path - a `verified` decode the
  app independently confirmed (`exactCodeEvidenceVerifiedByApp`, `fetched_source`) but single-provider + barcode-DB
  source - below the 80 threshold, so it went to Needs Review while the feed still showed the "verified" badge =>
  "Verified AI Decode + Product '-' + Unknown".
- **Fix A (fast path):** `appVerifiedStrongEvidence = decision.status==="verified" && exactCodeEvidenceVerifiedByApp`
  carries auto-save regardless of tier/single-provider/threshold; only real blockers stop it (verified-catalog
  conflict, no usable name, junk source [weak tier], vendor code, private data, no exact evidence).
- **Fix B (scoring):** app-confirmed strong evidence adds +30 and SKIPS the Tier-3 supporting cap, so the stored
  evidenceScore is realistic. The cap still applies to weak/AI-only/non-exact evidence.
- **UI guard:** if a decode says "verified" but does NOT auto-save, the feed row decodeStatus is rewritten to
  needs_review - a "Verified AI Decode + Unknown" row can no longer exist. Exact-evidence-without-a-usable-name now
  shows the explicit reason "Exact barcode evidence was found, but no usable product identity was returned."
- **Live-confirmed** (2 calls): 7705471100046 + 816218028015 both return `verified` + `exactCodeEvidenceVerifiedByApp`
  + `fetched_source` + single_provider + Tier-3 sources in ~8s - exactly the shape the fix auto-saves.

## Hotfix: decode diagnostics + open-web source discovery (2026-06-14)
- **Two-stage decode, fast path untouched.** Stage 1 (local/catalog/alias -> barcode-DB pageFetch ->
  gemini-flash/gpt-5-mini, early-exit on first usable product) is unchanged and adds NO new calls on
  success. Stage 2 (AI-cited URLs first, then Firecrawl) runs ONLY on a Stage-1 miss. Rationale: the
  reported failure was never the fast path - it was the *absence* of any fallback when the DBs miss.
- **Open-web discovery via Firecrawl, gated + capped.** Chose Firecrawl (REST, `/v2/search` + `/scrape`)
  over direct Google scraping (Google blocks bots; ToS). Enabled only when `FIRECRAWL_API_KEY` is set;
  absent -> `search_provider_unavailable`, never a blocker. Capped <=3 scrapes/failed barcode. Always
  mocked in tests - zero live credits in CI. Playwright is PROOF only, never a runtime lookup engine.
- **Stop swallowing provider errors.** `.catch(() => {})` replaced with captured `ProviderStatus`. We
  must be able to tell rate-limit / timeout / error / no-match apart - that distinction is the whole fix.
- **Honest reason codes over one generic string.** The app NEVER says "not found" when a provider failed.
  `product_not_found_after_search` is emitted only after a search/read was actually attempted. The store
  prefers the server's honest `reasonText` over the generic gate text on the Needs-Review row.
- **SSRF safety on every arbitrary URL.** AI/Firecrawl can return any URL, so all are filtered through
  `isSafePublicUrl` before fetch (block loopback/private/link-local/CGNAT/metadata/file/non-http(s)).
- **AI-cited URLs are first-class evidence.** They are passed to the reader as `extraUrls`; a
  "Product Not Found" page that only echoes the code is rejected so it can't masquerade as a match.
- **Process lesson encoded as a rule.** Ground-truth product existence + the source that has it BEFORE
  changing decode thresholds/timeouts. Never assert "not found" from weak engines (Bing/DDG) or hidden
  provider failures. (See LESSONS_LEARNED.md.)

## Hotfix pt.2: deep + parallel fallback, separate budgets (2026-06-14)
- **Separate budgets, not one.** Normal scans must stay fast, so the fast path keeps its ~13s budget and
  never calls Firecrawl on success. Only a hard-failed barcode enters the deep fallback (AI 25s grounded
  + Firecrawl, ~30s hard cap). This is the owner's explicit rule: fast path fast, hard fails get depth.
- **Race, don't chain.** The old fallback chained AI-cited-URL reading THEN Firecrawl, which stacked to
  60s+. Now the deep AI re-run and Firecrawl run concurrently via `raceFinders`; the first VERIFIED +
  usable result wins and the losers are aborted. Wall-clock = the fastest finder, not the sum.
- **Fallback is stricter than the fast path.** The fast path trusts a usable AI name (speed). The
  fallback requires app-VERIFIED exact-code evidence before it stops early (`requireVerifiedEarlyExit`),
  because a slow deep result must be trustworthy, not a guess.
- **Coverage over the barcode-DB noise.** Real listings (Faire) rank below barcode-DB pages, so Firecrawl
  now opens 6 candidates IN PARALLEL and PREFERS product URLs over search/cart/login pages. Sequential
  top-3 was both too shallow (missed #4) and too slow (56s).
- **Cache so a barcode never re-pays.** A server-side decode cache returns a previously-found product
  instantly. The durable cache is still the client catalog/alias layer; this stops repeat spend in-process.
- **Honest to the end.** Added `fallback_coverage_missed` (searched but couldn't open the result that may
  have held the product) and forced the needs-review reason to the honest text, never the generic string.

## Phase 1: benchmark approach (2026-06-14)
- **API-level runner, not 100 browser runs.** The expensive thing to measure (latency, lookup path,
  cache, Firecrawl/AI cost) is the decode ENGINE, which lives behind `/api/ai-lookup`. The runner hits
  that route headlessly (fast, scriptable, sequential to mimic scanning). Playwright proves the UI on a
  REPRESENTATIVE set, not all 100 (per owner's instruction).
- **No fake barcodes.** No 100-code list existed; rather than invent live codes, we built the full
  harness + templates and validated on the 4 real codes we have ground truth for, then asked the owner
  for the real list. Honest accuracy: never "correct" without `expectedName`/`Brand`.
- **Cost guard reserves Firecrawl credits up front.** A cache-abort could otherwise hide spend; we
  reserve worst-case (1 search + maxScrape) then refine to actual, so the 400-credit guard can't be
  under-counted. Safe to over-count.
- **Cache hit => zero spend by definition.** A cached payload still carries the original credit number;
  cache confirmation keys off `debug.cached`, not the stored credits (fixed a false-negative).
- **Phase 2 cost model: catalog-page harvest, not per-barcode search.** Phase 1 showed tires would each
  cost ~7 Firecrawl credits via per-barcode fallback (~35k for 5,000). Phase 2 plans bulk catalog-page
  harvesting to amortize cost per record, measured by a 100-record pilot before any scale. See
  PHASE2_TIRE_DB_PLAN.md.

## Launch MVP Phase 1: Supabase foundation (2026-06-14)
- **Local Supabase, not cloud** (owner). Ports remapped to 553xx because Windows WinNAT reserves the
  default 542xx range ("socket access forbidden" on 54322).
- **RLS helper recursion-safety**: `is_member`/`has_role` are SECURITY DEFINER + `SET search_path=''`,
  owned by postgres (BYPASSRLS), so their internal read of memberships does not re-trigger memberships'
  RLS -> no recursive loop. EXECUTE granted to `authenticated` only.
- **Proof via authenticated user clients** (owner guardrail): service role used ONLY to create/delete
  test users; all isolation assertions run as real signed-in User A / User B sessions.
- **E2E auth bypass is production-impossible**: `NODE_ENV==="production"` short-circuits it off; browser
  path needs an explicit `NEXT_PUBLIC_E2E_AUTH_BYPASS` set only in the Playwright webServer. Proven by a
  unit test. Kept the 11 e2e specs green without coupling them to a live Supabase.
- **Scope held**: scan/count/sync NOT rewired to Supabase this phase (owner). Auth state kept OUT of
  scanStore to avoid destabilizing the proven scan path; repositories are the Phase-2 seam.
- **Tables jsonb catch-alls**: unknown_code_reviews.suggested + settings.data hold the sprawling
  suggested*/settings fields so the schema stays lean; repos map in Phase 2.

## Backend pivot: Supabase -> Firebase (2026-06-14)
- **Firebase over Supabase** (owner: existing Google/Firebase account). Done before real users/data, so
  no data migration - replace the foundation outright.
- **Emulator-first, secret-free**: a `demo-` project runs the full proof offline. No service account, no
  web config, no cloud project this phase. Real cloud + deploy deferred (needs approval).
- **Subcollections /businesses/{bid}/... over top-level collections.** Top-level tenant collections can't
  securely support `list` (Firestore `resource` is null during query authorization -> evaluation error).
  Path-based tenancy makes get/list/create/update/delete uniformly enforced by `isMember(bid)` from the
  PATH and makes forged-businessId writes impossible by construction. (Owner spec allowed non-top-level.)
- **Membership docs keyed `${businessId}_${uid}`** so rules check membership with a single exists()/get()
  (no collection query inside rules; no recursion).
- **Admin SDK server-only**; client never imports it; keySafety enforces it. E2E bypass reused unchanged
  (production-impossible).
- **Roles owner|admin|counter|viewer** per the owner's model.

## Decode ladder v2: cost-ordered rungs, Gemini out of decode (2026-07-08)
- **Ordered rungs, first settled answer stops the ladder** (`src/server/upc/ladder.ts`): local tire
  corpus / decode cache (free) -> `goupc` -> `fetchv2` -> `gpt` (GPT-5.5). Owner rule: never pay for
  a rung when an earlier one already answered. Every rung that ran records its reason, surfaced in
  the decode payload and Settings.
- **Go-UPC is GTIN-gated at the caller**: the rung is only added for a real GTIN shape with a valid
  GS1 check digit, so `runLadder` stays shape-agnostic and vendor/internal codes never hit the paid API.
- **Gemini is permanently out of decode.** Grounding billed every EXECUTED search query (~$14/1k)
  while `webSearchQueries` reported only cited ones (~100x undercount, see LESSONS_LEARNED L11), and
  it has no tool-call cap. Settings explicitly labels Gemini "not used for decode".
- **Daily cap charges paid rungs only** (`2dcf714`): corpus/cache hits are free; the counter is an
  atomic storage-backed increment charged INSIDE the paid rung (one charge per genuine compute -
  fixes the route-level double-billing and cap-before-cache-read classes). Default raised 200 -> 500
  (owner authorized 2026-07-10); `AI_LOOKUP_DAILY_LIMIT` still overrides.
- **Cap-blocked scans are honest**: a 429/cap block shows its real reason, never "Unidentified item"
  masquerading as a resolver miss (an all-`other`/~10ms mass-scan pattern means cap exhaustion).

## Size-aware identity merge + evidenced brand families (2026-07-10)
- **Why:** on a 100-code preview run the server verified 99/100 but the UI counted only 40 - every
  additional SIZE of an already-seen tire model collapsed into a fuzzy "link to existing product?"
  suggestion, and `086699998538` fired a false prefix conflict (Go-UPC said "Michelin", prefix owner
  "bfgoodrich" - the same company).
- **Sizes live in specs, not names.** Corpus product names are slugs (`wrangler_steadfast_ht`), so the
  name-parse tire rule never fires. `findIdentityMerge` now derives size from `specsShort`/`specsFull`;
  size-distinct fuzzy matches MINT NEW PRODUCTS instead of queueing review suggestions. scanStore
  passes the decoded specs into the merge (`1782c11`).
- **Brand families are evidence-backed corporate ownership**, not lookalike names: Michelin owns
  BFGoodrich + Uniroyal (NA), Continental owns General, Goodyear owns Cooper; Dunlop unfamilied after
  the 2025 Sumitomo trademark purchase. `sameBrandFamily` feeds `evaluatePrefix` so shared GS1
  prefixes inside one company never conflict. (Prefix->company is many-to-one: one company owns many
  prefixes across many countries.)
- **Never weaken a real-conflict path:** unrelated brands (Michelin vs Goodyear) still conflict.

## Suggested-identity display + high-trust auto-apply (2026-07-09)
- **Show the candidate, decouple it from counting.** Suggested identities render on the scan feed and
  Your counts with a "(suggested)" tag only when confidence is genuinely low (< 0.8). Counting stays
  gated: high-trust suggestions (>= 0.8 or app-verified exact code) auto-apply to the COUNTED row
  (`c232b5d`); everything else remains review-first. Rationale: a review row showing "92%" was a
  VERIFIED decode a store safety gate had held - the UI just never said so; now the reason + barcode
  are visible (Needs Review barcode column, Status column on Your counts).
- **Corpus slug names are prettified at display time** (digit model-code rule bounded to short
  tokens; hyphen parts cased individually) - stored identity is unchanged.

## Count snapshots persist for every access level (2026-07-12, owner-ratified)
- `countSnapshots` (variance report) stays in the shared persisted store for ALL roles. Sanity-check
  performed and passed: snapshot lines carry ONLY productId / display name / qty (scanStore.ts
  snapshotCount) - no raw codes, no aliases, no provider diagnostics - so the customer data firewall
  is not widened. Cap 12 bounds growth. Revisit only if snapshot lines ever gain code-bearing fields.

## CSV import: merge-by-sku-alone stays (2026-07-12, owner-ratified)
- A CSV row with a SKU matching an existing product and NO barcode merges quantity into that product.
  Rationale: the CSV is the owner's own human-supplied list (same trust basis as the approved-alias
  rule); SKU is a human-assigned identity in their catalog. Guardrails unchanged: barcode conflicts
  never re-point (error list), idempotent re-import, preview + explicit confirm. Revisit if
  multi-tenant catalogs ever share SKUs across businesses.

## Master-catalog trust: suggestions fall through, only strong verifieds replay (owner, 2026-07-22)
- `ladder_verified_strong` master-catalog entries still replay as VERIFIED - the append gate already
  demanded app-verified exact-code evidence >= 0.8 on a public barcode before writing one, so replaying
  it is safe. A suggestion-class master-catalog hit NEVER settles the ladder by itself anymore: it
  records `master_catalog_suggestion_fallthrough` and the scan falls through to the remaining rungs.
- Rationale: the rung was self-poisoning. Its own 0.85-confidence suggestion writes were being replayed
  forever as settled answers, permanently blocking the paid rungs from ever re-attempting a real
  decode for that code.

## Deployment model: GitHub disconnected, manual/CLI deploys only (owner, 2026-07-22)
- GitHub is disconnected from Vercel; deploys are manual/CLI only going forward (owner order, in
  response to tonight's deploy-chaos incident). Previews intentionally stay mock/no-login -
  `NEXT_PUBLIC_FIREBASE_*` is deliberately absent from the Preview environment. Production promote is
  always an explicit owner action, never automatic on push/merge.

## Auto-resolve stamping must never override a deliberate human hold (owner, 2026-07-22)
- Post-decode resolved-stamping must never fire on rows a store safety gate deliberately holds open -
  `suggest_link` fuzzy-match candidates and dedup/alias conflicts stay visible in Needs Review even
  after a decode result lands, until a human actually resolves them. Fixed on
  `fix/rung-trust-and-resolve-stamp` by skipping the stamp for rows carrying `suggestedLinkProductId`
  or `lastAliasConflicts`.
