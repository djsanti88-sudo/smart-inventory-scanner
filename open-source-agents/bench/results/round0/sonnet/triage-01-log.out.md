# Triage: cloudDrainRace.store.test.ts failure

## What the log actually shows
Exactly one test failed out of 350: `cloud drain race (regression) > does not lose ops enqueued while an async drain is in flight`, asserting `applied.length` equals 8 but getting 7. Every other file, including the directly related `ledgerInvariants.store.test.ts` (8/8 passed), is green. The test drives `Promise.all([drain1, drain2, lateEnqueue])` and then reads `mockDb.getAppliedOpIds()`.

## True root cause: this is not flakiness or environment noise — it is the exact race condition the test exists to catch, and it just reproduced

The test's own name is "does not lose ops enqueued while an async drain is in flight" — a regression test explicitly written to prove that an op enqueued *while a drain is running concurrently with another drain* still ends up applied. The assertion failing with "7 instead of 8" means one operation is missing from `getAppliedOpIds()` after the concurrent sequence completed — i.e., a real op was silently dropped during a concurrent drain, which is precisely the failure mode this regression test was built to catch. This is not a broken assertion or a bad test — it is a genuine, reproduced data-loss bug in the drain/enqueue interleaving logic under real concurrency (two drains racing plus a late enqueue landing mid-flight).

Do not mistake this for infra flakiness because of the surrounding noise in the log (see below) — the failure is deterministic in what it demonstrates: something in the drain implementation has a window where a late-enqueued op is not picked up by either in-flight drain and not caught by a subsequent one either, so it never gets marked applied. This is consistent with a classic TOCTOU (time-of-check-to-time-of-use) bug: if a drain snapshots "pending ops to send" at the start and a new op is enqueued after that snapshot but before the drain finishes and clears its processed set, the new op can be enqueued and then immediately (incorrectly) treated as already covered by the in-flight drain's completion bookkeeping, or the two concurrent drains "race" to decide which of them is responsible for a newly enqueued op and neither claims it.

## What is noise, not the cause
- `System.gc information: heap used 612MB / 1024MB` — informational memory telemetry, not indicative of an OOM or resource failure causing this specific assertion mismatch.
- `MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 close listeners added to [EventTarget]` — this is a real warning worth separate follow-up (it suggests something, likely in test setup/teardown or the mock DB/drain machinery, is adding listeners without removing them across the 8 parallel worker threads), but it is a warning, not a thrown error, and it did not fail the test run on its own — all 47 other files passed cleanly in the same run despite this warning being present. It should be tracked as a secondary hygiene issue (potential listener leak under repeated test/worker execution), not conflated with the counting bug. It is plausible but not proven from this log alone that the same code path causes both; treat them as two separate findings unless further evidence links them.
- The 8-thread worker pool config is standard Vitest parallelism, not itself a cause — though it is worth noting concurrent execution across threads can sometimes surface real races that a single-threaded run would mask, which is arguably *why* this regression test was written and *why* it's now catching something real, not a reason to dismiss the failure as thread-pool artifact.

## Recommended next action
1. Do NOT retry-until-green, skip, or loosen the assertion (e.g., changing `toBe(8)` to `toBe(7)` or adding a tolerance) — that would hide a real data-loss bug matching this project's own ledger/sync invariants (every enqueued op must eventually be applied exactly once, never dropped).
2. Root-cause the drain implementation under test: inspect how `drain1`/`drain2`/`lateEnqueue` interact — specifically what "pending ops" snapshot each drain takes and when, and whether an op enqueued between a drain's snapshot and its completion can end up unclaimed by any drain. This is a concurrency/ordering bug in production drain logic, not a test bug, given the test's explicit purpose.
3. Separately, investigate the `MaxListenersExceededWarning` (11 close listeners on one EventTarget) as its own hygiene finding — likely a missing listener cleanup in test/mock teardown that should be fixed regardless of the counting bug, since it could eventually cause real leaks or masking of other issues in CI as suite size grows.
4. Because this is a regression test for exactly this class of bug, treat the failure as a release blocker for any code touching the cloud drain/sync path until the missing-op window is fixed and the test passes deterministically (run it several times, not just once, to confirm the fix closes the race rather than just narrowing the window).
