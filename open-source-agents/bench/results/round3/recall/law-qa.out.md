**Answer Key – Scanbin Inventory Project**

| # | Question | Answer (rung) |
|---|----------|----------------|
| **Q1** | What is the TOP‑LEVEL LAW governing scanned codes and the scan feed/count? | **[recalled]** Every scanned code—whether known, unknown, misread, random, undecodable or trust‑rejected—must immediately appear on the scan feed and be counted. The `ensureProvisionalCount` routine runs synchronously before any decode/AI/network call in `scanStore.processScan`. |
| **Q2** | Which module in `src/services/resolver.ts` decides a scan is “known”, and what are the ONLY two conditions under which it returns `known`? | **[recalled]** The function `resolver.ts`’s `resolveKnown()` (or equivalent) returns `known` only when: 1. an approved alias exists (`alias.approved===true`) or 2. a product is verified (`product.verified===true`). |
| **Q3** | Is an AI/mock decode result ever allowed to be auto‑saved as an alias? | **[recalled]** No – AI/mock results are only suggestions; they never get auto‑saved as aliases and never mark a scan “known”. |
| **Q4** | What is `applyScanEventOnce` and what field on `InventoryCount` does it use to guarantee idempotency? | **[recalled]** `applyScanEventOnce` is the dedupe ledger that records applied scan events. It uses the `scanEventIds` array on `InventoryCount` to ensure a ScanEvent is only counted once. |
| **Q5** | When is an idempotency key generated for a ScanEvent, and is it ever regenerated on retry? | **[recalled]** The idempotency key (`${businessId}:${sessionId}:${scanEventId}:${operation}`) is generated at scan time and is never regenerated during retries. |
| **Q6** | What is the real decode orchestrator file, and what is the deprecated file that should NOT be extended? | **[recalled]** The active orchestrator is `server/decode/pipeline.ts`. The legacy/deprecated file to avoid extending is `services/lookup.ts` (or similar “legacy lookup” path). |
| **Q7** | List the decode ladder rungs in cost order, from the first free rung to the last paid rung. | **[recalled]** 1️⃣ L1 – In‑memory cache<br>2️⃣ Tire corpus exact hit<br>3️⃣ Retail corpus (GTIN‑shaped)<br>4️⃣ Learned‑products tier (always “suggested”, never “verified”)<br>5️⃣ L2 Turso/libsql cache<br>6️⃣ Free half: upcitemdb → openfoodfacts (own counters, never daily cap)<br>7️⃣ Lazy daily‑cap gate (between free/paid halves)<br>8️⃣ Paid half: goupc (GTIN‑gated) → fetchv2 (open‑web) → gpt |
| **Q8** | What stops the decode ladder from continuing to the next rung? | **[recalled]** The first rung that settles with a “verified” or “suggested” result stops the ladder; subsequent rungs are not evaluated. |
| **Q9** | What is the current status of Gemini in the decode pipeline? | **[recalled]** Gemini is permanently disabled (`GEMINI_DECODE_DISABLED=true`). It only survives in legacy lookup mode and re‑check, but never participates in the main ladder. |
| **Q10** | What does the daily AI cap (`AI_LOOKUP_DAILY_LIMIT`) charge, and what never gets charged against it? | **[recalled]** Only paid rungs are charged; free/corpus/cache hits never burn a slot. |
| **Q11** | Where (relative to which stages) is the daily cap charge actually applied in `pipeline.ts`? | **[recalled]** The charge occurs inside the paid path via `chargeDailySlot` (`services/security/aiSpendGuard.ts`) called from `server/upc/storage.ts`. |
| **Q12** | What is `checkAndIncrementDaily` and should new code call it? | **[recalled]** It is a legacy file‑only gate for the lookup mode. New code should NOT call it; instead use the paid‑path counter in `pipeline.ts`. |
| **Q13** | What does `markWrong` actually do to inventory quantity – is it a delete? | **[recalled]** `markWrong` deactivates bad aliases, un‑verifies the product, and re‑points feed events onto a fresh “Unidentified item” via `incrementInventoryCount`. It never deletes or zeroes counts; total physical quantity remains invariant. |
| **Q14** | What two data‑layer/database technologies coexist in this project, and what does each one store? | **[recalled]** 1️⃣ better‑sqlite3 – static knowledge corpus (tire/retail data, local `.db.gz` on Vercel).<br>2️⃣ Turso/libsql – decode cache (L2) plus ladder usage/daily‑cap counters. |
| **Q15** | What must automated tests NEVER do regarding AI providers, and how is this enforced in E2E tests specifically? | **[recalled]** Tests never call live providers; unit tests mock engines/fetch. In E2E, `IS_E2E=1` forces `/api/ai-lookup` to use the mock route regardless of keys, ensuring no real provider calls. |
| **Q16** | In the evidence verification hierarchy (`EvidenceVerifier`), list the four (or more) strength tiers from weakest to strongest. | **[recalled]** None < url_only < snippet < grounding_chunk < fetched_source. |
| **Q17** | What are the requirements for `decideDecode` to return “verified” (list all conditions)? | **[recalled]** 1️⃣ Public barcode shape (never X00/FNSKU/vendor/internal).<br>2️⃣ Strong app‑verified evidence (single provider or two agreeing).<br>3️⃣ Non‑empty identity.<br>4️⃣ Confidence ≥ 0.8. |
| **Q18** | Before sending data to an AI provider, what categories of information must the deterministic sanitizer mask? | **[recalled]** Phones, emails, obvious names, cost/price/margin patterns – any PII or obvious identifiers are masked before AI calls. |
| **Q19** | X00/Amazon FNSKU/ASIN codes and vendor‑style labels – can they ever be treated as UPC/EAN/GTIN codes? | **[recalled]** No – such vendor labels are routed to “Needs Review” unless a human‑approved alias exists; they never count as UPC/EAN/GTIN. |
| **Q20** | Trap question: which gate, cap, breaker, or firewall in this codebase is allowed to suppress a scanned row from appearing on the feed or from being counted? | **[recalled]** The `ensureProvisionalCount` guard (idempotency/dedupe) and the daily‑cap (`AI_LOOKUP_DAILY_LIMIT`) can prevent a scan from counting, but no other gate should. In practice, only the idempotency check in `scanStore.processScan` stops a row from appearing or being counted. |

**All answers are based on the provided Scanbin crib sheet.**
